# 0.2 Change Request 004 — Smoke slices: diff-derived tests that accumulate into a release

Status: AUTHORIZED (Mike, 2026-08-14). Companion to CR-003; same Phase 3 entry
wave. Applies to both lines — the kungfu half needs no substrate change and can
run on 0.1.x immediately.

## The picture

Every change carries its own smoke test, written from its own diff. A release's
smoke set is the union of the slices in it. Nobody maintains a release test
plan, because the release test plan is assembled from what actually landed.

Today the org has a fixed conformance census (`enforcement-smoke-set-spec`, 64
fixtures) and an eval corpus (`golden-jobs-v1`). Both are curated corpora that
drift away from what changed. Neither answers "what does THIS release need
exercised."

## Decisions

**D1 — The slice is written by the producer, from the diff.**
Whoever produced the change writes a smoke slice: the shortest runnable check
that would fail if this diff regressed. It is inference work (only a mind knows
what its change actually risks), recorded as an artifact bound to the exact
commit, with its command and expected outcome.

**D2 — Agreement happens inside the review gate that already exists.**
The reviewer countersigns the slice as part of the same exact-commit review it
already performs. `reviewed-clean` gains one clause: *and this slice covers the
change*. That is the whole agreement system. No new ceremony, no separate
sign-off round, and the countersignature is already commit-bound.

**D3 — The release set is derived, never maintained.**
The smoke set for a release is the union of slices over the release range
(`<last tag>..<tip>`), computed by the same landings probe CR-003 §6 installs.
There is no registry to fall out of date: if a commit is in the range its slice
runs, and if it is not, its slice does not.

**D4 — A landing with no slice blocks the release.**
This is the forcing function, and it mirrors the mergedown card. A commit in the
release range with no countersigned slice is a release blocker, so coverage is
complete by construction rather than by diligence. The lawful exit is a filed
no-slice declaration with its reason (docs-only, CI config, revert), recorded
the same way as a no-landing declaration.

**D5 — Running the set produces receipts, not a green feeling.**
Each slice run files a receipt against the release: the command, the digest of
what came back, who ran it, and how long it stays good (CR-003 D1/D2). A slice
that cannot run files `unknown` and blocks, rather than being counted as pass.

**D6 — Tiering is the org's, not the substrate's.**
Which slices are cheap enough to run per-merge versus only at release e2e is
policy data an org tunes (razor). Ship the mechanism with a single tier and let
the tiering land as data.

## Why this composes rather than adds

The slice is an artifact, the countersignature is a verdict clause, the release
range is CR-003's landings probe, and the run results are CR-003's receipts.
Nothing here is a new bone. It is the world-fact law applied to the question
"was this release exercised", with the same three properties: recorded at the
moment it is cheap, re-derivable by a third party, and able to say unknown.

## Checklist

- C1 slice artifact bound to an exact commit, carrying command + expected
  outcome.
- C2 `reviewed-clean` extended with the coverage clause (D2).
- C3 release set derived from the landings probe over the release range (D3).
- C4 sliceless landing blocks the release; no-slice declaration is the exit
  (D4).
- C5 slice runs file receipts; `unknown` blocks (D5).
- C6 tiering ships as policy data, single tier at v1 (D6).
- C7 kungfu: producer writes the slice, reviewer countersigns it — written into
  coder and reviewer guidance in BOTH lines.

## 0.1 adoption

C7 alone is the 0.1 half and needs no substrate work: producers write a slice
with their completion, reviewers countersign it in the review they already file,
and the release owner assembles the set by hand from the release range until the
probe exists. Start with 0.1.8.
