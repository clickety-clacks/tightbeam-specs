## Goal

Give each commit in the frozen `0.1.9` source range exactly one explicit disposition
for `0.2.0`. Preserve the feature meaning, dependencies, rationale, evidence, status,
and follow-up for each source SHA.

Treat a whole `0.1.9` feature that is absent from `0.2.0` as a parity defect. Keep that
feature in an actionable `USE AS-IS`, `REFACTOR+APPLY`, or `RETHINK` row until the
target work is complete. Do not silently convert absence into `OMIT`.

Make reconciliation a landing-time duty. Before a future commit becomes reachable
from `origin/0.1.9`, the owner of that landing records its disposition row with the
fields defined in Architecture. A patrol can compare Git history with the ledger and
report a missing or duplicate row without judging the disposition.

## Non-Goals

- This plan does not implement a source change on `main`, `0.1.9`, or `0.1.8`.
- This plan does not move a product branch, tag a release, release, deploy, or change
  live state.
- This plan does not create feature work items or assignments.
- This plan does not authorize a cherry-pick, merge, refactor, or rethink. Mike elects
  each cross-line landing separately.
- This plan does not make merge topology a product feature. It dispositions each merge
  commit so the range is exact, while constituent non-merge rows govern product work.
- This plan does not claim that a patrol, rail, hook, or cross-repository transaction
  exists. The maintenance control is a written duty plus a reproducible read-only check.
- This plan does not reopen the rejected real-fixture exception. Commits `7ae16ed4` and
  `94d62522` form a source-line add/remove sequence.

## Terms

- **Split point**: commit
  `cd72fe0b06404afc6619a800c84a6a7eea595baa`, where the product lines diverged.
- **Frozen source tip**: commit
  `73e1e3b45d53fe84d879a51a77acbbd7a9567bf1`, the observed
  `origin/0.1.9` tip for this census.
- **Source universe**: each commit returned by
  `git rev-list --reverse <split-point>..<frozen-source-tip>`.
- **Inventory**: `0.2.0-cross-line-reconciliation-inventory.tsv`. Its `source_sha`
  column is the exact-once key.
- **Target**: the `0.2.0` product line on `main`. A disposition describes target impact;
  it does not authorize target mutation.
- **Feature-level parity**: each final feature or hardening present on `0.1.9` either
  exists on `main` with equivalent or stronger behavior, or has an actionable target
  disposition. A merge carrier, revert pair, line-only release mechanism, or legacy
  migration does not create a target feature by itself.
- **OMIT**: make no target change. An OMIT row names evidence that the target already
  has equivalent or stronger behavior, that the source effect was later reversed, or
  that the effect belongs only to the `0.1` line.
- **USE AS-IS**: preserve the source behavior and tests through a separately authorized
  target landing. Normal context edits do not change the behavior.
- **REFACTOR+APPLY**: preserve the source requirement and regression floor, but express
  them through the target architecture.
- **RETHINK**: preserve the problem and evidence, then derive the target behavior from
  `0.2.0` principles before implementation.
- **Landing owner**: the person or agent accountable for the operation that first makes
  a future source SHA reachable from `origin/0.1.9`.
- **Patrol check**: the read-only comparison in the audit document. It reports set or
  cardinality differences. It does not choose a disposition.
- **Follow-up link**: a durable work-item, assignment, spec, commit, or artifact
  reference. `none` means the row needs no further target work.

## Architecture

### Exact inventory

The TSV is the canonical commit ledger. It has these columns:

1. `ordinal`: stable order within the frozen `git rev-list --reverse` output.
2. `source_sha`: full Git SHA and the exact-once key.
3. `responsible_owner`: owner of the disposition or target follow-up.
4. `source_subject`: Git subject, preserved for feature recognition.
5. `disposition`: one value from `OMIT`, `USE AS-IS`, `REFACTOR+APPLY`, or
   `RETHINK`.
6. `target_impact`: the target behavior or the reason no target mutation is due.
7. `evidence`: exact commits, current files/tests, or an audit section.
8. `status`: `COMPLETE`, `PLANNED`, or `DESIGN-REQUIRED`.
9. `follow_up`: durable link or `none`.

The TSV uses one row per commit. Rows may share a feature-group label only when each row
still carries its own full SHA, subject, target impact, evidence, status, and follow-up.

### Disposition groups

The inventory retains the original four-bucket rubric and updates stale outcomes against
current main. The main groups are:

- **OMIT — target already equivalent or stronger**: credential rollback, adapter-death
  recovery, assignment file projection, spec homing, holder-verdict selection, decision expecter preference,
  external-agent CLI guidance, terminal decision parity, notice batching, priority and
  effort handling, golden-rule guidance, Toplines Lane 1, and the gate-preflight fixes.
- **OMIT — source effect reversed or line-only**: merge topology, `0.1` release and CI
  mechanics, `0.1.7`/`0.1.8` migration code, source-line schema provenance, the reverted
  model-election guidance, and the rejected real-fixture add/remove sequence.
- **USE AS-IS**: active-branch numeric resolution and package host-metadata purity.
- **REFACTOR+APPLY**: wake cancellation provenance; GitHub authentication after the
  credential-store and policy seams are re-homed; doctor credential-health reporting;
  history-complete public-rule compatibility; and universal-root publication hardenings
  `11203c86` plus `10ea356a`. The required audits also place resident-harness smoke
  redelivery, structured marker facts, and retired-session transactional notice markers
  here.
- **RETHINK**: execution evidence as process custody; host toolchain needs through host
  facts; and unstaffed-role refusal through office addressing.

The inventory records smaller groups and their exact evidence. The audits document explains
the three formerly unsupported OMIT rulings.

### Landing-time maintenance duty

For each future `0.1.9` landing, the landing owner performs this sequence:

1. Resolve the candidate's full source SHA before the branch update.
2. Add one TSV row with every required field.
3. Record current target evidence and choose one rubric value.
4. Mark unresolved target work `PLANNED` or `DESIGN-REQUIRED` and add its durable follow-up.
5. Publish the reviewed specs change before the product branch update makes the SHA reachable.
6. Perform the patrol check after the product update and record its output with the landing
   evidence.

This sequence is the maintenance duty. No hook or rail currently enforces it. The patrol
command detects omission after a history read; the landing owner and reviewer enforce the
pre-landing order.

### AC-01 — The frozen range is exact

Given the owned Tightbeam clone at the frozen refs, when the reviewer runs the range commands
in the audit document, then Git reports 179 total commits, 154 non-merge commits, and 25 merge
commits.

### AC-02 — Each source commit has exactly one row

Given the frozen Source universe and the Inventory, when the reviewer runs the exact-once
check, then it reports `missing=0`, `duplicate=0`, `unknown=0`, `malformed=0`, and
`rows=179`. The ordinal and source-subject replays each report zero mismatches.

### AC-03 — Each row is buildable as a decision

Given any inventory row, when a target owner reads it, then the row supplies a full source
SHA, source subject, responsible owner, one rubric value, target impact, evidence, status,
and a follow-up value.

### AC-04 — OMIT requires evidence

Given an OMIT row, when the reviewer follows its evidence, then the evidence proves one of
three outcomes: equivalent-or-stronger target behavior, a reversed source effect, or a
line-only effect.

### AC-05 — The three required audits control their dispositions

runs audits A1 through A3, then the evidence shows:

  `markerTo`; row 24 is `REFACTOR+APPLY`.
- A3 proves main's transaction and Firehose ordering behavior, then finds that current main
  omits the source test's retired-session durable marker; row 18 is `REFACTOR+APPLY`.

No audited row retains OMIT without complete evidence.

### AC-06 — The hardenings remain actionable

Given inventory rows 171 and 172, when the reviewer reads them, then both name
`REFACTOR+APPLY`, status `PLANNED`, the main-origin universal-root publication feature, and
their distinct retry and pending-unlearn behavior.

### AC-07 — A whole missing feature cannot disappear into prose

Given a final `0.1.9` feature that current main lacks, when the reviewer follows its row, then
the row is actionable and names the target effect plus a follow-up. The package-purity,
doctor-health, public-rule-history, and identity-publication-hardening rows satisfy this
check for the newly exposed gaps.

### AC-08 — A future landing is patrol-checkable

Given a future SHA newly reachable from `origin/0.1.9`, when patrol compares the updated Git
range with the ledger, then it finds exactly one row for that SHA. The row names the landing
owner, target impact, evidence, status, and follow-up.

### AC-09 — No unbuilt enforcement is claimed

Given the plan and audit files, when the reviewer searches for the maintenance mechanism,
then the documents identify a written duty and read-only commands only. They do not claim a
hook, rail, background patrol, or atomic cross-repository update exists.

### AC-10 — Candidate identity is immutable for review

Given the committed specs candidate, when the parent opens review, then the review assignment
names the exact candidate commit, this file path, this file's SHA-256, both audit artifact
paths, and their SHA-256 values. A byte change requires a new exact-revision review.
