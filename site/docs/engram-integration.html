The home is shared

Current Tightbeam homes are per host and harness:

~/.tightbeam/homes/gibson/codex
~/.tightbeam/homes/gibson/claude

Multiple archetypes use these homes. Guidance and elected skills are applied per session. Creating one Engram index per archetype would duplicate storage and misrepresent this topology.

The agent has a stable key

Tightbeam's append-only pointer history connects native harness sessions to the stable Tightbeam session key. I verified this join with a real Codex transcript and a real Claude transcript.

A directory, native session ID, archetype name, and Engram tape ID each describe a different thing. Keep those distinctions in the integration.

The smallest useful integration

Keep native transcript ingestion. Export a compact context manifest that relates the host, harness, native session ID, and Engram tape versions to the Tightbeam session key. Include assignment and dispatch references only where records establish them.

A companion tool can prove result enrichment first. A reusable integration should give Engram a supported context import/read interface and expose the mapping through a narrow Tightbeam export. It does not need a new transcript format or a new identity system.

Keep metadata out of the code fingerprint index. Agent identity and coordination links should be small keyed records. Re-indexing every identity bundle, prompt, skill, and work-item description would recreate the storage problem.
Existing configuration fields can cover the transcript roots

This example is for Gibson and has not been installed. Each host needs its own actual base directory and configured name.

db: ~/.engram/tightbeam/index.sqlite
tapes_dir: ~/.engram/tightbeam/tapes
additional_stores: []
watch:
  debounce_secs: 5
  ingest_timeout_secs: 120
  log: ~/.engram/tightbeam/watch.log
  sources:
    - path: ~/.tightbeam/homes/gibson/codex/sessions
      pattern: "*.jsonl"
    - path: ~/.tightbeam/homes/gibson/claude/projects
      pattern: "*.jsonl"

The watcher handles new file events. It does not backfill existing history on startup, and it skips absent directories. Inventory archives and older home layouts explicitly. Keep generated tapes outside every watched root.

Why an Engram dispatch marker alone is incomplete

Engram's existing lineage mechanism needs the same UUID in both the sending tool call and receiving message. Tightbeam's stored IDs do not automatically create those markers. A small producer bridge could support future dispatches, but historical traffic needs explicit relationships from the retained records.

I recommend the metadata and causal-link route for complete attribution. A forward-only marker bridge remains a smaller optional integration. Agent ancestry and native harness subagents need separate treatment from an actual Tightbeam delegation.

Evidence and limits

I checked the live gateway version, matching source, fetched main, Engram's watcher/adapters/query projection, read-only Tightbeam metadata, and real native-session joins. No index rebuild, integration deployment, or full adapter test was performed.

The recon includes the configuration example, source revisions, proposed mapping fields, and a bounded proof covering shared homes, native session changes, cross-host collisions, real edits, and historical identity gaps.
