# Learning from Tightbeam changes

Proposal, 8 September 2026. This document answers Mike's request to record what we theorize, change and observe so future agents can evaluate it and improve the system again. It proposes a working practice using existing specifications, release history and execution records. It installs no evaluator, changes no rail and creates no new worker reporting gate.

## Operating model

Ship the best-supported product design we can establish for people to use. Record why we chose it, implement it coherently, review it and verify its acceptance requirements before release. The later external forensic review tests our expectations against actual use and informs the next version. It is continuous product improvement, not permission to ship an incomplete design and wait for users to discover whether it works.

Distinguish three claims: the design is well justified; the implementation meets its release requirements; actual use supports the predicted improvement. Source analysis, domain judgment and pre-release verification support the first two. Later operational evidence informs the third. Do not demand future usage evidence before selecting a design, or use its absence to lower the release bar.

The unit is a meaningful product/design change, not every commit, agent turn or receipt. Several commits may implement one hypothesis. Several hypotheses may ship together. Preserve that grouping so future agents do not attribute a package's result to one isolated rule without evidence.

## One discoverable change record, with linked evidence

Keep a short learning ledger for each release in the canonical specs repo, linked from its release plan and the relevant governing specs. Use stable identifiers, such as H019-01, so code changes, release notes, observation reports and later decisions can refer to the same hypothesis. Ordinary workers need the ask and applicable local facts, not the ledger in every prompt.

Each entry answers six questions:

1. What failure prompted this change? Record the intended protection or benefit, concrete examples and the baseline evidence. Include Mike's corrections and earlier attempts, especially when the proposed change removes a rule with a useful original purpose.
2. What do we believe will improve, and why? State the predicted behavior, the competing risk and what would count against the hypothesis. Distinguish a demonstrated source defect from a theory about agent behavior.
3. What are we changing? Name the actual guidance, kungfu rule, substrate mechanism or combined change. Link the chosen design and implementing commits. Record deviations from the proposal, other changes shipping alongside it and its reversal path. Until chosen, label unselected changes as proposed.
4. Who actually experienced it? Record release/code version, actual loaded rule and guidance versions where observable, participating agent/model/harness versions, scope and exposure dates. A published release, an edited identity file and an agent actually running those instructions are different facts. Mark unknown or mixed exposure explicitly.
5. What happened? Link a representative set of completed, failed, abandoned and still-open cases, relevant trace/query snapshots, actual user or production outcomes, and evidence gaps. Keep evidence that contradicts the hypothesis. Do not count only successful completions or volunteers.
6. What did the external assessment find, and what did the responsible agents decide? Record a dated, scoped judgment: supported, mixed, contradicted or inconclusive. Explain the evidence, uncertainty, harms and next action. Keep, revise or reverse is an agent decision within existing authority. Link the next hypothesis/version and the next review point when a question remains.

Start with a concise hypothesis and references. Delivery and evaluation fill in the later answers when those facts exist. Do not require agents to fabricate a complete outcome report before work can begin. Revise working details normally, but preserve dated decisions, exposure records and assessments; corrections identify what they supersede. Git history supports this, while explicit links make the important lineage understandable without reconstructing every commit.

## Evidence without another paperwork process

Reuse execution, assignment, artifact, review, wake, denial and deployment records. Store the relevant query or extraction version, time window and retained evidence snapshot with the assessment so later agents can reproduce the reasoning after the live state changes. Preserve report/artifact bytes as well as links. Ask agents to record judgments that cannot be inferred, such as why a broader specification was necessary, in their existing brief or decision record.

Collect product outcomes alongside process costs. For comparable kinds of asks, examine elapsed time to a usable outcome, actual rework and escaped defects, unnecessary spec/review effort, avoidable escalation, missed PO influence, and unfulfilled waits. Separate active work from provider outages or unrelated dependency delay when the data supports it. Counts of assignments or reviews are signals to inspect, not universal limits or automatic quality scores.

Classify cases by the ask, uncertainty and consequences, not by the light/heavy label the agent selected. Otherwise the system grades its own classification. Use a small independently examined sample to establish whether additional process was useful. Include both a routine repair and a small but consequential change. Known severe regressions need attention even if an average improves.

Compare with representative pre-change cases when available, and report selection differences, model changes, other released features and unequal exposure. A controlled rollout or matched replay can improve attribution when practical; it is not a mandatory new evaluation platform. With a bundled release, judge the combined behavior first, then investigate which changes explain it. Do not call a before/after association causal proof.

Missing observations remain missing. The pinned b299 dispatch code appends denial records through a best-effort path, and the recent audit did not establish live cached rule or hook versions. The implementation should name any minimal instrumentation needed to evaluate a hypothesis. No denial row is not proof no denial occurred. A missing counter is not zero. Record capture gaps and avoid comparisons whose denominators cannot be established.

### Stall and churn detection classes

Use these classes for later comparison. They are diagnostic hypotheses, not automatic fault findings or authority to replay, replace an owner, edit live state or change service power. Record the first observed signal, the evidence that confirms or rejects the class, the affected obligation, the useful state change that ends the interval and any work spent without such a change. One episode may carry more than one class.

| Class | Candidate signal | Confirmation and confounders | Later question |
| --- | --- | --- | --- |
| S1: terminal-but-unfinalized turn | A turn remains `running` after its harness process or journal has recorded a terminal result. New turns queue behind it. | Confirm from the durable turn row and independent terminal evidence. Do not classify a merely long turn this way. On 8 September, turns `126359`, `126361`, `126370`, `126372`, `126378`, `126390` and `126391` all ended in `usageLimitExceeded`; finalization then rejected a health assignment attributed to the wrong affected session. Five affected lanes held 43 queued turns at 16:44 UTC, rising to 45 on a later read. | After the replacement is installed, can the same owner-child failure commit a truthful terminal state and let the lane drain without a DB edit, service restart or blind replay? |
| S2: queue-head blockage | One old running row persists while the same session's queued count grows and no later turn starts. | Confirm that the head has made no terminal or useful progress and that the lane enforces ordering. Distinguish this from an active long task and from unrelated queues on other sessions. | Does detection happen before several prompts accumulate, and does supported recovery preserve their order and unknown-effect status? |
| S3: completed decision without delivery | An owner records an actionable answer, but the actor that must use it receives no supported handoff. | Compare the owner's terminal response with wakes, messages and the recipient's subsequent work. A delivered but delayed wake is not this class. | Do decisions reach the accountable actor without an external agent copying the answer across the seam? |
| S4: obligation without a live continuation | An open assignment has no capable holder activity, pending condition, scheduled wake or explicit pause tied to a real dependency. | Read the work graph, assignment, holder, recent turns, wakes and owner disposition together. Silence on the parent's own row is insufficient. Exclude a parent as false-dark only when all three facts exist: an open child, a pending child continuation and a parent record naming that wait. Two of three remains an inference. | Do patrols restore ownership before the commitment is threatened, without repeatedly waking intentionally paused work? |
| S5: shared substrate interruption | Several independent lanes fail near the same DB, gateway, adapter or host event. | Establish a common timestamped substrate event. Similar provider errors or a healthy service check alone do not prove a shared cause. | Does recovery restore both service availability and affected obligations, with unknown outcomes reconciled? |
| C1: same-evidence review repetition | Another review or full test gate runs against the same candidate identity with no new requirement, code, evidence or reviewer mandate. | Compare exact tree, patch, base, test-log identity and review scope. Similar task names are insufficient. A changed tree may justify a successor review. | How often is existing evidence reused, and how much review or test work repeats without changing a decision? |
| C2: premature review and candidate churn | A review opens before the producer freezes the full candidate or settles known dependent design questions, then a successor review becomes necessary. | Reconstruct candidate ancestry and why each tree changed. Distinguish planned component reviews from reviews invalidated by predictable integration work. | Could the work have used component checks in parallel, then one combined review after a declared freeze? |
| C3: policy or contract oscillation | Successive revisions alternate because two applicable rules, schemas or owner interpretations demand incompatible behavior. | Name both controlling statements and the affected seam. A reviewer finding an ordinary implementation defect is not policy conflict. | Was the conflict resolved once by an accountable ruling before more code and review, and did tests encode the selected meaning rather than both incompatible forms? |
| C4: duplicate execution race | Two agents can start the same expensive verification, implementation or publication operation before cancellation or ownership exclusion takes effect. | Inspect both live processes and queued future-start instructions. Two proposed workers are not duplicate execution if only one can start. | Did allocation and cancellation become effective before launch, and was one result retained rather than rerun? |
| C5: notification and retry churn | Wakes, reminders or retries repeat against unchanged state without a new consequence, evidence or due obligation. | Group by obligation and state snapshot, not prompt wording. Separate distinct delivery failures and deadlines from unchanged reminders. | Did fewer notifications preserve timely attention and completion, rather than merely hide stalled work? |
| C6: unproductive token burn | Agent turns repeatedly reload broad context, reproduce settled evidence, rerun covered gates or discuss the same blocker without a useful state change. | Record model usage where available and use turn count, repeated inputs, duplicate commands and unchanged outputs as bounded proxies where it is not. Long reasoning that produces a consequential ruling or defect finding is not automatically waste. | Did the newer process reduce tokens per useful outcome while preserving defect discovery, independent review and safe recovery? |

Treat detection as a stateful claim, not a label applied in hindsight. Each recorded episode starts as `candidate`, becomes `confirmed` only when the confirmation column is satisfied, and ends as `resolved`, `still open` or `false positive`. Preserve the timestamps and evidence for every transition. For churn, also record the last useful state before the repeated work and the first useful state after it. This makes later analysis capable of measuring detection delay, wasted turns or gates, time to resumed work and false-positive suppression.

Compare the observed state with the obligation's declared next event. Time is evidence only in that context.

### Comparison at the authorized installation-plus-seven-days review

Conduct the follow-up on schedule even if the evidence is sparse. For each hypothesis record actual installed software, loaded guidance/rules and affected agent exposure. A week after installation may contain less than a week of relevant use. Compare similar asks and failures, include unresolved cases, and keep the following questions in the external report:

1. Did the DB-timeout, terminal-finalize, child-restart, full-process exit or per-session queued/no-running signatures recur? Record the observed sequence and affected outcomes; do not infer the same root cause merely from the same shutdown string.
2. How long did safe recovery take? Distinguish first failure, detection, first useful resumed work, reconciliation of unknown effects and fulfillment of the affected obligation. Report missing timestamps and still-open intervals. Service uptime or a running turn is not the completion timestamp.
3. Were unknown outcomes preserved and reconciled before unsafe replay? Inspect actual external effects, authorized repair lineage and late callbacks. Count observed duplicate effects separately from duplicate messages, proposed staffing and prevented races.
4. Did internal POs and accountable agents restore capable ownership and carry results forward without external intervention? Record each external diagnostic, routing, succession, design or verification intervention that was needed. Include decisions answered locally but not delivered to the actor who must execute them. Fewer interventions only supports improvement if work still completes safely; unattended stalled work is not success.
5. Did the revised guidance, rails and actual served projections agree? Recheck current spirit opportunity, proportionate small fixes, honest early review, evidence applicability and the canonical-runner case. Keep actual product/credential/publication holds distinct from stale workflow instructions.
6. Did reminders become less repetitive while preserving attention to distinct obligations, changed consequences and delivery failures? Compare successful continuation and missed work alongside notification volume. Fewer notices after removing a gate or during a dead delivery path do not establish success.
7. Did recovery avoid the commissioning and start races observed here? Examine pending future-start instructions as well as live processes. Record whether the system made ownership and cancellation effective soon enough to prevent duplicate work, including mistakes by external supervisors.

The evaluation records a dated supported, mixed, contradicted or inconclusive judgment with its next responsible action. It can finish without declaring the treatment successful. Persistent defects and unmet delivery commitments retain owners. These observations inform the next design; they do not automatically change rails or waive release acceptance. ## Example: the posture design decision

Problem: agents have put small understood bugs through full specification/review cycles. Light/heavy posture was introduced to prevent this. The current predicates accept either token, while guidance defaults uncertainty to heavy.

Hypothesis: making proportionate execution an explicit orchestrator responsibility, removing that default and preserving the direct small-fix path can reduce unnecessary process without increasing substantive defects. The selected design removes both token gates with the composed guidance changes. Exercise the contrasting acceptance cases before release; retain actual outcomes for later external assessment.

Compare an understood checkout-depth CI correction, a one-line authorization change and work with actual architectural uncertainty. Record the chosen work, why extra process was useful where invoked, time to usable outcome, failures/rework and the independent assessment of adequacy. Do not classify the authorization change as light merely because its diff is small, or the CI correction as heavy merely because it touches infrastructure.

A first assessment might be mixed: routine repairs became simpler, but uncertain tasks were expanded too slowly. That would justify refining escalation of consequential uncertainty, not declaring the entire philosophy false or reinstating every old gate. This is an illustrative possible finding, not observed data. The actual assessment must cite real cases and preserve contrary findings.
