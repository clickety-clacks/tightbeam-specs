# Artifacts & reconciliation — v1

Status: RATIFIED DIRECTION (Flynn 2026-07-22, refined 2026-07-23). The general answer to
"where do specs live" — a spec is one ARTIFACT kind; this subsystem records every
deliverable's existence as a provenance-linked row, and on cleanup archives the whole
workspace if it holds artifacts (no forced relocation), keeping them findable later
("that banana spec from yesterday"). Composes with the session lifecycle
(retire/cascade/reap) and the accountability constitution. UNBUILT; design.

## The problem

Artifacts (specs, reports, docs, data) are created in a session's WORKSPACE (its
durable-scratch workdir). That workspace is a disposable projection — it moves with the
session and is removed when the session is reaped. So a deliverable left in the
workspace is dropped between the boards when the workspace closes, and nothing records
it existed. And a consumer given "the spec at its canonical path" has no path: there is
no resolution mechanism (verified — specRefName is an unresolved string).

## The essence (MVP — Flynn 2026-07-22)

Physical placement is a wash: a shared NFS folder is no more findable than an archived
workspace. The ENTIRE win is tying an archived workspace (and its artifacts) to the WORK
RECORD. The canonical query the substrate must answer, exactly and without search:

    "where is the spec generated by ticket xyz?"
    → work-item xyz → artifact(kind=spec) → its `home` (inside the archive). Done.

The floor follows §2's one rule — the record decides (Flynn ruling 2026-07-24,
adjudication #5, superseding an earlier "archive every closing workspace" draft
sentence that predated the simplification):
- FLOOR: a closing workspace with recorded `in-workspace` artifact rows is archived,
  tied to the work-item edge THE ROWS THEMSELVES carry. A closing workspace with no
  artifact rows is removed — if it was producing something owed, there's a record; if
  there's no record, it wasn't. Archiving unrecorded workspaces would fill storage
  with unlabeled boxes tied to guessed-at tickets.
- ENHANCEMENT (recording discipline): individual artifacts recorded with edges → the
  query returns the EXACT file's home, not "the workspace, go look."

Consequently BOTH placement-policy (§3) and topic-search (§4) are pure OPTIONAL
enhancements. Placement matters only when an artifact must physically LIVE in an external
system (a spec in the repo for version-control/tooling) — an integration need, never a
findability one. An org that writes no policy and remembers ticket ids loses nothing.

## 1. The artifacts registry — a provenance graph, not a file index

The registry's value is NOT that it lists files with metadata (that is just inodes — a
folder you search by filename). Its value is the EDGES tying each artifact to the
CONVERSATION and INTENT that produced it — the one thing a filesystem cannot hold, and
the thing that lets a human find an artifact by the discussion they remember rather than
a filename they don't. The file/home is the least interesting node; the edges are the
point.

New `artifacts` table. The load-bearing columns are the PROVENANCE EDGES (all cheap
exact FKs):
- `createdBySession` → the session that made it; `recordedMessageId` → the EXACT
  transcript turn where the artifact-record event fired (anchors it to the relevant
  slice of conversation, not the whole transcript)
- `workItemId` → the intent it serves (→ transitively its originating user request);
  `parentSession` → the spawner responsible at cleanup
Plus the descriptive/locating fields:
- `artifactId`, `kind` (spec | report | doc | data | other), `title`, `description`
- `originPath`, `contentSha256?`
- `state`: `in-workspace` (freshly made, in the live workspace) | `archived` (in
  tightbeam custody, in the archive) | `released` (handed out of custody — see §3;
  the row persists, but tightbeam no longer tracks where the bytes live)
- `home?` — while `archived`, the archive path the substrate stores and returns; once
  `released`, tightbeam stops asserting a location
- created/updated timestamps
DISCIPLINE (guidance now, rail where rows allow): when a session produces a deliverable
worth keeping — not scratch — it files an artifact row (`tightbeam artifact-record
--kind … --title … --path …`). The agent judges deliverable-vs-scratch; the substrate
records what it is told. A spec's artifact row IS the resolution of specRefName: a
work-item's spec-ref points at an artifact; "the spec's canonical path" = its `home`.

## 2. Cleanup = archive-if-artifacts (no forced relocation)

CORRECTION (Flynn 2026-07-23): earlier drafts framed this as a GATE that blocks
workspace teardown until each artifact is relocated to a "proper" home. That was
pre-record thinking. Once existence is a durable ROW and archiving is always valid,
there is nothing to force. The default is trivial:

- When a session is cleaned up (reap): if it has any `in-workspace` artifacts, ARCHIVE
  THE WHOLE WORKSPACE to an archive folder and flip those rows to `archived` with their
  archive `home`. If it has none, just remove it. That's the entire default.
- No relocation ceremony, no per-artifact "proper home" step, no blocking, no
  parent-notification requirement. Archiving always succeeds, so teardown is never
  stuck, and nothing valuable is ever dropped (the row + the archived bytes both
  survive, fully findable via the provenance edges).
- The org/user MAY add steps to their own cleanup process (relocate specs to a repo,
  push reports to NFS) — but that is opt-in enhancement they author, never something
  the substrate imposes. Archive + record suffices.

## 3. Relocating out of the archive = leaving tightbeam's custody

CORE MODEL (Flynn 2026-07-23): there are two states, and the boundary is custody.
- IN CUSTODY: the artifact lives in tightbeam's archive worktrees. Tightbeam knows
  where it is and can hand it back later. This is the default and needs no config.
- OUT OF CUSTODY: someone (usually the user) wants the file to live somewhere else —
  a repo, an NFS share, their own folder. The moment it leaves the archive, tightbeam
  STOPS tracking its location. The provenance ROW survives (who made it, for what work,
  from what conversation — the valuable graph is permanent), but tightbeam no longer
  claims to know where the bytes are.

The substrate does NOT model placement policy, does NOT relocate files, and does NOT
try to keep a location record correct after a move — it cannot watch the filesystem,
and pretending to would be a lie. Relocation is entirely the user's/org's business.

The ONE obligation is guidance on the AGENT: before moving artifacts out of the
archive, it must tell the user plainly — in warm, non-alarming terms — that those
files are leaving tightbeam's safekeeping and the user is now the one keeping track of
them. Nothing is lost or broken; it's just a hand-off. Recommended plain-language
notice (ELI5, do not scare the user):

> "Heads up: I'm putting these files in <place> for you. Once they're there, they're
> in your hands — tightbeam keeps tabs on things it stores itself, but not on files
> out in your own space, so if you move or rename them later it won't know. Nothing's
> lost, everything's right there where I'm putting it; it just lives with you now
> instead of in tightbeam's back room. Sound good?"

This lives as ARCHETYPE GUIDANCE (any agent that relocates artifacts), not a rail —
it is a courtesy-and-clarity duty, not something the substrate can enforce.

## 4. Discoverability — we promise the RECORD, not a search feature

The contract (Flynn 2026-07-22): tightbeam is not trying to be a better filesystem, and
it is not going to lose track of shit. The substrate PROMISES that it KNOWS — records,
as rows — that these artifacts are products of THIS work, THESE agents, and (via
`recordedMessageId`) this conversation. That topology is the deliverable. USING the
topology to find an artifact later is an exercise for some other technology, layered on
top; the substrate promises no search functionality.

What the substrate itself answers (exact FK traversal over its own rows, no search):
- "where is the spec generated by ticket xyz" → work-item → artifact → `home`
- "what did session S produce" → session → artifacts
- work-item / session filters over registry rows — exactly those two, because those
  are the two questions the record exists to answer.

What is explicitly SOMEONE ELSE'S layer (all optional, all built ON the recorded
topology, none a substrate dependency): full-text search over transcripts or titles,
semantic/vector recall, an agent grepping the archive. These may be good; the spec
promises none of them. Nothing in tightbeam breaks in their absence, because the common
question ("output of ticket xyz") never needed them.

## 4b. Git under the hood — the BRANCH is the artifact (Flynn 2026-07-22)

Worktrees are SUBSTRATE PLUMBING, not an org-level concept: they exist solely to
prevent trampling when multiple agents edit one repo/branch simultaneously — the
substrate's file locking. Folding worktree outputs into the target branch is mechanical
substrate work, SQUASH-MERGED BY DEFAULT so under-the-hood micro-commits never pollute
the history the org sees — CONFIGURABLE (org/user setting, e.g. `worktree_fold_strategy:
squash | merge`) for orgs that want the full commit trail. Squashing loses no
provenance either way: attribution is a tightbeam row (constitution guarantee 1),
never a git commit trail.

The org-visible deliverable is the BRANCH — an artifact like any other (registered,
provenance-edged to its work-item/sessions). What happens to it — PR, merge to main,
release — is ORG/USER POLICY, outside the substrate. Nothing prevents tightbeam from
orchestrating many agents into one branch; deciding how that branch reaches main is
never the substrate's job.

Residuals stay in their proper homes: textual conflicts that survive `--files`
disjointness are WORK (a work-item routed to a mind, not a merge mechanism); "does the
integrated branch build" is the orchestrator's verification duty (archetype guidance).

## 5. Composition & what this closes
- Resolves the tier-3 spec-storage homework gap: specRefName resolves via the artifact
  registry; guidance's "the spec at its canonical path" becomes real.
- The WV lane's pause (Sol couldn't reach a spec) is this gap in the field — an
  implementer resolves a spec by its artifact `home`, fetched from the substrate.
- Closes the multi-coder INTEGRATION-OWNERSHIP underdesign: worktrees are plumbing,
  the branch is the registered artifact, merge-to-main is org policy (§4b).
- A workspace holding artifacts never silently vanishes: cleanup archives it and the
  rows survive — not by blocking teardown, but because archiving is the default and
  always succeeds.

## Non-goals (v1)
- Not a content store: artifacts live in their homes (repo, NFS, archive); the registry
  holds POINTERS + provenance, not bytes (assets table remains the separate blob store).
- No search functionality promised: the substrate records provenance topology and
  answers exact traversals; any search/recall technology is an external layer on top.
- No auto-detection of artifact creation: recording is a deliberate act (agent judges
  deliverable-vs-scratch); a rail can later require it where a lane's output is expected.
